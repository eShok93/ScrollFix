# Release trust checklist

The public v0.1.0 preview is ad hoc signed, not notarized, and used an identifier-only designated requirement. Source changes do not modify that binary. Do not call it a verified release.

1. Build from a reviewed, fixed commit with an Apple-issued **Developer ID Application** certificate. Set `SCROLLFIX_CODESIGN_IDENTITY` to that identity, `SCROLLFIX_EXPECTED_TEAM_ID` to the 10-character Apple team ID, and `SCROLLFIX_REQUIRE_DEVELOPER_ID=1` when running `./scripts/build-app.sh`. The script must fail if no suitable identity is configured.
2. Notarize the app with Apple's notary service and staple the accepted ticket. This requires maintainer credentials and is intentionally not performed by the local build script.
3. Run `SCROLLFIX_EXPECTED_TEAM_ID=... ./scripts/verify-release.sh build/ScrollFix.app`. It checks code-signing integrity, the exact bundle and signature identifiers, the expected Apple team, the Developer ID authority, the stapled ticket, and Gatekeeper assessment. Do not publish an artifact that fails any check.
4. Package the verified app, extract the archive into a clean directory, run the same verification on the extracted app, calculate the archive's SHA-256, and update both READMEs with the exact version, architecture, and hash. Do not silently replace an existing release asset.
5. Explain the permission migration: users of v0.1.0 should remove the old ScrollFix entry from macOS Accessibility/Device Control and grant access to the new Developer ID signed app. Apple records the app's designated requirement when permission is granted, so the old entry can retain the earlier weak identity.

The optional autoscroll also needs a real mouse with a middle button and must be checked on supported macOS versions before binary release. Check the normal middle-click tradeoff, combined direction filter, screen sleep, full sleep/wake, session switch, and reconnect. No synthetic scroll or button event should be stored as a history.

For local QA, build with `SCROLLFIX_BUILD_KIND=qa ./scripts/build-app.sh`. This produces `build/ScrollFix-QA.app` with bundle ID `app.scrollfix.mac.qa`, a visible QA label, and no login-item control. It is ad hoc signed and needs its own macOS permissions. Do not register this disposable bundle for launch at login or distribute it as a release. If an older QA build with the production bundle ID is already registered as a login item, unregister it before replacing that build; then install the verified production app at a stable path and register that copy.
When that path is already in use, set a fresh lowercase `SCROLLFIX_QA_VARIANT` such as `v7` to build `build/ScrollFix-QA-v7.app` with its own bundle ID `app.scrollfix.mac.qa.v7`. Every existing QA output and symlinked output directory is rejected. Never delete a QA bundle merely to reuse its variant: ad-hoc signing produces a version-bound designated requirement, so an old privacy grant may not match a rebuilt app with the same identity. Stop the previous QA process before launching the new variant because two taps would otherwise overlap. Grant the new identity its own macOS permission; for repeatable released builds, use a stable Developer ID signing identity. See [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

References: [Apple code-signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), [Apple notarization](https://developer.apple.com/documentation/security/notarizing_macos_software_before_distribution).
